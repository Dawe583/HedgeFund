# Strategy validation sweep — 2026-11-25

Full validation-gate sweep: all four ported bots × two symbols × two timeframes,
365 days of Binance spot klines, default seed 42. Every run executed with
`--app-db sqlite:////tmp/sweep-final.db` — `backend/data.db` was never touched.

## Setup

- **Data**: Binance public REST (`api.binance.com`, no key), venue `binance` for all
  four ingests. Candles upserted into `backend/data/research.db` (the designated,
  replaceable candle store).
- **Coverage**: BTCUSDT 4h 2194 rows, ETHUSDT 4h 2190 rows, BTCUSDT 1h / ETHUSDT 1h
  8760 rows each; all spanning 2025-11-25 → 2026-11-25 (full 365 days, no gaps in
  ingest). Synthetic fallback was **not** needed.
- **Gate** (`trading/research.py`, design §7): VALIDATED requires all of — ≥ 30 trades,
  Monte Carlo permutation p (Sharpe) < 0.05, bootstrap Sharpe 95 % CI lower bound > 0,
  walk-forward majority of windows profitable. 1000 permutations, 1000 bootstrap
  resamples, 5 walk-forward windows, seed 42.
- **Methodology note**: `permutation_p` / `sharpe_actual` come from the trade-ordering
  permutation test (per-trade returns, annualised); `sharpe` / `ci_lo` / `ci_hi` come
  from the equity-curve bootstrap (per-bar returns, annualised). Different return
  bases — the magnitudes are not directly comparable; what matters is the gate logic
  applied to each.

## Interpretation

**No strategy passes the gate on any market — nothing goes to paper.** That is the
gate working as designed: several rows *look* tradeable on headline metrics and are
correctly stopped by the statistics.

**Closest to the gate** (fail permutation + bootstrap only, pass trades count and
walk-forward majority):

1. `hft BTCUSDT 4h` — best headline of the sweep: PF 1.685, Sharpe 1.549, max_dd
   −10.1 %, walk-forward 4/5, bootstrap P(positive) 0.937. Yet permutation p = 0.542:
   **half of all random reshufflings of the same trades do as well or better**, and
   the CI lower bound is −0.47. The edge, if any, is in the trade PnL magnitudes, not
   in anything the ordering/timing adds — indistinguishable from luck.
2. `breakout BTCUSDT 1h` — 317 trades, PF 1.115, Sharpe 1.129, wf 3/5; but p = 0.545,
   CI [−0.75, 3.01]. High trade count yet no statistically separable edge.
3. `breakout BTCUSDT 4h` — lowest permutation p of the sweep (0.259) with positive
   returns, still 5× above the 0.05 bar; CI lower −1.01.
4. `scalp ETHUSDT 4h` — PF 1.314, Sharpe 0.883, smallest drawdown (−9.8 %), wf 3/5;
   but p = 0.906 is near-worst — random orderings beat it 90 % of the time.

**Uniformly negative evidence:**

- Every single permutation p is ≫ 0.05 (best 0.241). No bot's trade sequencing shows
  evidence of skill rather than luck on this data year.
- Every bootstrap CI lower bound is ≤ 0 — even the best rows cannot exclude a
  negative true Sharpe at 95 % confidence.
- **meanrev is catastrophically broken on crypto**: PF 0.52–0.70, Sharpe −2.5 to
  −10, max drawdown 67–100 % of equity, 0–1/5 profitable windows, bootstrap
  P(positive) ≈ 0. On 1h it takes ~1000 trades and effectively zeroes the account.
  Not a tuning problem — the strategy thesis (fading overextensions) is structurally
  wrong for a trending/volatile market; candidate for redesign or removal from the
  paper-trading roster entirely.
- **scalp/hft/breakout sit in the "plausible but unproven" band**: positive-return
  rows exist (mostly 4h, BTCUSDT), but the statistics say they cannot be
  distinguished from noise at this sample size. The gap to close is permutation p —
  everything fails there first.
- Timeframe effect: 4h rows are uniformly healthier than 1h rows for scalp/hft/
  breakout (fee + noise drag dominates at 1h). ETHUSDT is uniformly worse than
  BTCUSDT for breakout and scalp.

**Caveats**: one year of data, default (unoptimized) strategy parameters, seed 42,
spot klines. Rejection here means "no evidence of edge", not proof of no edge — but
per design §7, REJECTED never reaches paper. The honest next moves: parameter search
with the same gate, longer history (4h rows are only 2190 bars — thin for
annualisation), and a hard look at whether meanrev should survive at all.

## Reproduction

```bash
cd backend
for combo in "BTCUSDT 4h" "BTCUSDT 1h" "ETHUSDT 4h" "ETHUSDT 1h"; do
  set -- $combo
  uv run python -m trading.research ingest --symbol $1 --timeframe $2 --days 365
done
for bot in scalp hft breakout meanrev; do
  for sym in BTCUSDT ETHUSDT; do
    for tf in 4h 1h; do
      uv run python -m trading.research validate --bot $bot --symbol $sym \
        --timeframe $tf --app-db sqlite:////tmp/sweep-final.db
    done
  done
done
```

Raw per-run payloads (full validation JSON incl. Monte Carlo path bands) are in
`/tmp/sweep-final/*.json` on the machine that ran the sweep; verdict rows with full
`validation_json` are in `/tmp/sweep-final.db` (`backtest_validations` table).
Neither is committed — both are regenerable via the commands above with identical
results (seeded).
